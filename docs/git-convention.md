# Git 컨벤션

Q-First 레포에서 브랜치, 커밋, 이슈, PR을 다루는 규칙이에요. 이 문서를 추가하는 것만으로 GitHub 설정(필수 리뷰, push 제한, 머지 방식)이 바뀌지는 않아요. 그 설정은 레포 Settings에서 따로 해요.

## 1. 브랜치

- 형식: `<type>/#<이슈번호>-<짧은-영문-설명>` (영문 소문자와 하이픈)
  - 예: `feat/#12-priority-list`, `fix/#20-null-quality-impact`
- 문서만 고치는 작업(`docs`)과 설정 작업(`chore`)은 이슈 번호를 생략할 수 있어요.
  - 예: `docs/master-doc-update`
- `main`은 팀이 함께 쓰는 기준 브랜치예요. `main`에 바로 push하지 않고 작업 브랜치에서 PR로 합쳐요.
- 작업 브랜치 하나는 이슈 하나, 또는 팀이 함께 리뷰할 수 있는 범위 하나만 다뤄요.

### 타입

| 타입 | 쓰는 경우 |
|---|---|
| `add` | 기능 동작 없이 파일이나 자료를 단순히 추가 |
| `feat` | 새 기능 추가나 기능 확장 |
| `fix` | 의도와 다르게 동작하는 부분 수정 |
| `docs` | 문서 작성과 수정 (마스터 문서, 설계서, README 등) |
| `refactor` | 동작은 그대로 두고 구조만 변경 |
| `test` | 테스트 추가와 수정 |
| `chore` | 도구, 의존성, 환경, 자동화 설정 |

- 브랜치의 주된 목적으로 타입을 정해요. 기능 브랜치에 테스트와 문서가 같이 들어 있어도 `feat`예요.
- 한 브랜치 안의 커밋은 서로 다른 타입을 써도 돼요.

## 2. 커밋 메시지

- 형식: `<type>/#<이슈번호>: <변경 설명>`
  - 예: `feat/#12: 비상·예고 목록 분리 표시`
- 이슈 번호가 없는 작업은 `<type>: <변경 설명>`으로 써요.
  - 예: `docs: 마스터 문서 추가`
- 타입은 소문자로 쓰고 콜론 뒤에 공백 한 칸을 둬요. 설명은 한글로 써도 돼요.
- 제목은 결과를 한 줄로 적어요. 이유나 주의할 점이 있으면 한 줄 비우고 본문에 적어요.
- 한 커밋에는 함께 리뷰하고 함께 되돌릴 수 있는 변경만 담아요.
- 다음은 커밋하지 않아요.
  - 비밀값(키, 토큰, 비밀번호)
  - 로컬 환경 파일(`.env` 등)
  - 인덱스, 캐시, 빌드 결과물 같은 생성 파일
  - 실제 회사명, 현업 원본 수치, 개인정보

## 3. 이슈

- 새 기능은 Feature 이슈 템플릿으로 만들어요. 제목은 `[Feature]`로 시작하고 목표를 적어요.
- 체크리스트는 작업하면서 갱신해요.
- Feature 템플릿은 `enhancement` 라벨을 써요. 레포에 이 라벨이 없으면 먼저 만들어야 해요.

## 4. Pull Request

- PR 제목은 커밋과 같은 형식으로 써요.
- PR 템플릿의 항목을 모두 채워요. 해당 없으면 `N/A`라고 적어요.
  - 관련 이슈
  - 작업 내용 (변경한 것, 이유, 확인 방법과 결과)
  - 스크린샷
  - 미완료 작업
  - 리뷰어에게
- `main`에 합쳐질 때 이슈를 자동으로 닫으려면 본문에 `Closes #N`을 써요. 참고만 할 때는 `Related to #N`을 써요. 완료한 이슈마다 `Closes`를 각각 적어요.
- 확인 결과는 실제로 한 것만 적어요. 문서 변경은 링크 확인, 내용 검토처럼 한 확인을 적고, 못 한 확인은 이유를 적어요.

## 5. 리뷰와 머지

- 작성자가 아닌 리뷰어 1명 이상을 권장해요.
- 핵심 변경과 주의해서 볼 곳은 "리뷰어에게"에 적어요.
- 리뷰 의견을 반영하고, 돌려볼 수 있는 확인이 통과한 것을 확인한 뒤 머지해요.
- 머지는 Squash and merge를 권장해요. 최종 커밋 제목도 위 커밋 형식을 따라요.
- 머지한 뒤에는 작업 브랜치를 삭제해요.
- 여럿이 쓰는 브랜치의 히스토리를 고쳐 써야 할 때는 관련 팀원과 먼저 합의해요.
