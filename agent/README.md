# 실제 탐지 + LangGraph 조사 (로컬 개발)

이 구현은 중간발표 MVP의 실제 동작 검증용이다. 통계 탐지 결과와 기존 센서 알람으로 사건을 만들고, Spring이 품질 규칙으로 등급을 계산한다. LangGraph는 예고 게시/기존 알람 수신 후 조사하여 점검 안내를 구체화한다. 에이전트는 등급·순위·설비 제어를 변경하지 않는다.

## 실행

저장소 루트에서 실행한다. 데이터는 저장소 외부에 유지한다.

```sh
python3.12 -m venv agent/.venv
agent/.venv/bin/pip install -r agent/requirements.lock.txt
# Ollama와 qwen3:4b가 로컬에 필요하다. 이미 설치된 모델은 다시 다운로드하지 않는다.
ollama pull qwen3:4b
QFIRST_DATASET=/absolute/path/qfirst_dataset_v8 agent/.venv/bin/python -m uvicorn qfirst_agent.app:app --app-dir agent --host 127.0.0.1 --port 18094
```

현재 작업 PC에서는 `agent/.venv` 대신 `../qfirst-local/.venv`를 사용한다. QFIRST_DATASET 기본값은 `../qfirst-local/data/qfirst_dataset_v8`. 모델 기본값은 `qwen3:4b`, 변경은 `QFIRST_MODEL`로 한다. 외부 API 키는 필요 없다. Ollama 주소는 루프백 및 지정된 로컬 Docker 호스트(`host.docker.internal`, `ollama`)만 허용하며 외부 LLM·외부 추적 서비스로 데이터를 보내지 않는다.

## 실제 실행 흐름

1. **탐지**: 센서 5종만 사용. 설비별 첫 240개의 1분 관측으로 median/MAD 기준을 고정한다. 이후 과거 방향 rolling 점수 40 이상 3회와 **같은 센서 최근 9개 중 7개 |robust Z| ≥ 2, 현재 |robust Z| ≥ 3**을 모두 만족하면 예고한다. 현재 센서가 복귀했는데 평활화 점수만 남은 경우는 새 예고를 만들지 않는다. 1분 관측을 가정하며 누락 시 누적 조건을 초기화한다. 점수 40은 검증된 고장 확률이 아닌 PoC 임계값이다.
2. **기존 알람**: 원본 `error_code`는 탐지 피처가 아닌 별도의 기존 알람 입력이다. 같은 사건의 예고→비상 이동에 사용한다.
3. **조사 등록**: Spring이 사건 ID, 설비 ID, 트리거, 판단 버전, 탐지 시각, 조사 기준 시각, 대표 센서를 보낸다. PostgreSQL 큐에 등록한 뒤 Spring 조사 워커가 `/investigations/run`을 호출한다. Python은 조사 결과를 반환하고 큐 선점·재시도는 Spring이 담당한다.
4. **필수 조회 노드**: 실제 센서 구간, LOT 검사, 개발용 점검 지침을 조회한다. 숫자를 모델이 만들지 않는다.
5. **모델 선택 노드**: 로컬 Ollama가 설비 로그 / 관련 부위 정비 이력 / 종료 중 다음 행동을 선택한다. 추가 조회 최대 2회, 같은 도구 반복은 거부한다.
6. **도구 실행**: 설비·시각 범위를 서버에서 강제한다. 미래 검사 결과, 아직 완료되지 않은 점검, 다른 설비를 모델이 임의로 조회하지 못한다.
7. **정리·검증 노드**: 모델이 기존 근거 ID와 점검 초점(측정 확인 / 제어 상태 확인 / LOT 추적)을 선택한다. 서버가 허용된 안내 문구와 조회 수치로 안내를 구성한다. 자유 생성한 원인·설비 제어 문장은 게시하지 않는다.
8. **Spring 반영**: 사건·조사 ID, 기준 시각, 근거 참조를 검사한다. 기본 안내와 조사 안내를 함께 저장하고 snapshotVersion을 올린다. 현재 순위는 유지한다. 예고 조사보다 새 비상 조사가 우선하며 늦은 예고 결과가 덮어쓰지 못한다.
9. **화면**: 실제 API를 폴링하여 조사 중→완료/실패를 표시한다. 상세에서 기본 안내와 구체화된 안내, 인용 근거를 비교한다.

## 데이터·범위 제한

- `anomaly_detection.csv`와 미리 만든 예고 시각은 탐지 입력으로 사용하지 않는다. `inspection_guide.csv`는 조회 시각 전에 완료된 관련 부위 점검 이력에만 사용한다.
- v8의 `Z` 표기는 실제로 KST 시각이라는 데이터셋 특성을 어댑터에서 보정한다. 다른 데이터의 UTC를 일괄 바꾸면 안 된다.
- v8은 분당 1개 생산을 가정하므로 LOT 시작 시각과 순번으로 생산 시각을 복원한다. 실제 공장에서는 제품/사이클 추적 기록으로 대체해야 한다.
- 설정값 변경·기동/정지 상세 로그는 없다. 현재 로그 도구는 알람·공정 ID·LOT 변경을 조회하며, 존재하지 않는 로그를 만들어 원인을 배제하지 않는다.
- 점검 지침은 개발용 후보이며 제조사/현업 승인 문서가 아니다. 정비 이력 일치는 원인 확정이 아니다.
- 조사 기준 시각은 고정한다. 14:00 조사 결과에 14:05 검사를 끼워 넣지 않는다. 품질 결과가 나중에 도착하면 등급은 재평가하지만 중간 MVP의 에이전트 조사 트리거는 예고·기존 알람 두 가지다. 오래된 조사 안내에는 기준 시각을 표시한다.
- 실행 중 최대 150초, 개별 모델 요청 60초, 출력 최대 256토큰/회, 그래프 최대 12단계. 실패하면 기본 안내 유지. JSON 구조만 맞는 것으로 승인하지 않고 근거 ID·시각도 검증한다.
- Compose 실행에서는 조사 입력·결과·도구 선택·토큰 사용을 PostgreSQL에 저장한다. 모델의 숨은 사고과정은 저장하지 않는다. 예전 독립 개발 모드만 `agent/var/`를 사용한다.
- PostgreSQL 영속 큐와 Spring 체크포인트 복구를 연결했다. Compose는 `QFIRST_DURABLE_WORKER=1`로 예전 Python 메모리 큐 등록을 차단한다. 인증·권한, 고가용성 및 부하 검증은 후속 작업이다.
- 센서 파일을 시작 시 읽고 점수를 미리 계산하지만 각 점수는 그 시각 이전 센서만 참조한다. API와 도구는 재생 시각 이후 레코드를 반환하지 않는다. 이는 파일 재생이며 실제 설비 스트리밍 연결이 아니다.

## 측정 결과 (v8, v2 개발 비교)

**후속 일반화 스트레스 검증에서 성능 한계가 확인됐다.** v1/v2를 고정하고 v8을 읽지 않는 합성 시나리오 2,520회를 비교했다. 정상 실행의 오경보 발생은 1,127/1,350 → 636/1,350으로 줄었지만, 이상 구간 내 신규 탐지는 1,050/1,170 → 974/1,170으로 감소했다. 특히 3~6분 실제 이상은 113/180 → 15/180, 3분 이상/3분 복귀 반복은 86/90 → 60/90이었다. 아래 v8 성공 결과를 일반화 성능으로 해석하면 안 된다. [검증 방법·유형별 결과·한계](docs/detector-generalization-2026-11-13.md). 이번 검증에서는 운영 탐지기를 수정하지 않았다.

| 항목 | 실제 계산값 |
|---|---|
| EQP-003 최초 예고 | 13:43 |
| EQP-003 기존 알람 | 14:15 |
| 선행 시간 | 32분 |
| 14:00 검사·등급 | 0/17, 예고 4등급 |
| 14:05 검사·등급 | 1/22, 예고 3등급 |
| 14:15 검사·등급 | 2/32, 비상 1등급 |
| 정상 일시 변동 5구간 | v1 5/5 → v2 0/5 (복귀 후 지연 발생까지 포함) |
| 이상 28구간 | v1·v2 모두 28구간 탐지 (시연 4개 포함) |
| 시연 제외 24구간 | 모두 탐지 유지, 13개는 같은 시각 / 11개는 1~4분 지연 |
| 시연 제외 알람 있는 이상 22구간 | 알람 전 탐지 16/22 유지, 선행 시간 중앙값 15.5분 → 14분 |
| 시연 제외 알람 없는 이상 2구간 | 모두 탐지 유지 |
| 전체 평가 대상 47,600행 | 이상 구간 밖 신규 예고 5건 → 0건 |

**v8을 이미 확인하며 튜닝한 개발 비교이며 독립 테스트 성능이 아니다.** 시연 4구간은 과거 모델에 맞춰 센서를 조정한 자료라 별도 표기한다. 5개 정상 변동은 제한적인 패턴이며, 더 긴 정상 변동에서는 오경보가 발생할 수 있고 짧은 실제 이상은 억제될 수 있다. 예전 4/5 평가는 변동 직후 발생한 한 건을 누락한 오류이며 정확한 v1 값은 5/5다. 점수 수식과 40 기준은 유지하고 센서별 예고 확정 조건만 변경했다. 기존 센서 알람은 기다리지 않는다. 이상 확정 센서와 9개 원천 기록을 근거로 남긴다. 중간 MVP에서 ML 모델은 선택 항목이므로 이번에는 학습 분류기를 붙이지 않았다.

기존 fixture(13:41, 0/19→1/24→2/34)는 시나리오 가정이다. 실제 실행 API에서는 고정하지 않는다. 최초 예고가 달라져 예고 이후 생산분의 검사 분모도 변한다. 미래/정답 데이터로 시연 시각을 맞추지 않는다.

## 검증

```sh
PYTHONPATH=agent ../qfirst-local/.venv/bin/python -m unittest discover -s agent/tests -v
PYTHONPATH=agent ../qfirst-local/.venv/bin/python agent/scripts/evaluate_detector.py
```

테스트는 미래 센서 변경에 대한 과거 결과 불변, 검사 cutoff, 근거 없는 응답 거부, 중복 작업 및 충돌 거부, LLM 장애 처리를 검증한다. 단위 테스트의 FakeLLM은 테스트에만 쓰고 애플리케이션은 Ollama를 호출한다. 평가 스크립트만 windows.csv 정답을 읽는다. 상세 비교 결과는 `agent/var/detector-comparison.json`과 `.csv`. `detector_v1.py`는 비교용 원본이며 실제 서비스는 `detector.py`의 v2를 사용한다. 과거 `detector-evaluation.json`은 누락이 있는 이전 결과이므로 최신 비교에 사용하지 않는다.

실제 LLM 포함 통합 검증은 `backend/scripts/check_replay.py`를 사용한다. 실행 방법은 backend/README.md 참고.
